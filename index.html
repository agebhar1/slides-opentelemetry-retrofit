Signals

  • Traces path of a request
  • Metrics measurement captured at runtime
  • Logs recording of an event
  • Baggage contextual information passed between signals

Traces

  • set of events
  • implicitly defined by spans
  • trace ≈ DAG of spans
  • req. concept of Context Propagation

Spans

  • name
  • SpanContext
  • parent's span identifier (0..1)
  • SpanKind
  • start/finish timestamp
  • Attributes [(k/v)]*
  • Links to causally-related spans  (0..*)
  • Events (timestamp, name, attribute*)*
  • Status
SpanContext
conforms to W3C Trace Context
  • TraceId 16-byte array; worldwide unique; group all spans for specific trace
  • SpanId 8-byte array; globally unique
  • TraceFlags bit mask; options for a trace: Sampled, Random
  • TraceState k/v pairs; vendor specific; see W3C Trace Context
  • IsRemote boolean; received from somewhere else or locally

Baggage

  • k/v store
  • propagated alongside context
    → available across service boundaries
  • ⚠ security
  • ≠ { span, metrics, logs } attributes
  • what it should it be used for?

Context Propagation

  • enables distributed tracing
  • aim: correlate signals with each other
  • propagation → moves context between services/processes

Setting the Scene

a custom, legacy C middleware

  • queue like middleware
  • ops: dis-/connect, read/write
  • C code base ≈ 32 years
  • single threaded, (Sun) TI-RPC ★
  • single host (not distributed)
  • clients uses dynamic library
  • ★  in the following, replaced by UNIX domain socket

Challenges

  • production critical
  • single threaded
  • no metadata/headers support
  • message can't be changed
  • context propagation?

    [ read(), … ]

Key Facts

  • keep span context in k/v store
  • identified by
